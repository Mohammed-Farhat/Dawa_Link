## 1. Time and calendar

| ID | Rule |
|---|---|
| R-T1 | All business logic uses **Asia/Beirut** time (DST handled by the time-zone database). Timestamps are **stored in UTC**. |
| R-T2 | **Opening hours:** a weekly schedule, 0–2 ranges per day `[open, close)`; `close` may be 24:00. They're used for: "open now" (early-release asks), the pickup deadline, and the Open/Closed badge. *(Closures, holidays and vacation mode are postponed.)* |
| R-T3 | **Request hours (N-5):** sourcing requests and watches can only be **created** during request hours. Outside them the client sees: "DawaLink searches during the day. Please come back tomorrow from 08:00." Searching and reserving listed stock work at any time. |
| R-T4 | **Pickup day and deadline:** the client chooses the **pickup day** (R-F3): today, or one of the pharmacy's next open days within its **pickup time** setting (N-6). The **deadline** = the closing time on that day, and **never after the box's expiry date**. *Example:* reserved Mon 10:00, the client chooses tomorrow, the pharmacy is open Tue 08:00–21:00 → Tue 21:00. |
| R-T5 | **A reservation's deadline never changes once set.** Editing the opening hours or the pickup time setting doesn't affect existing reservations. |
| R-T6 | **Offers use real time** (N-12), and notifications are sent immediately. |
| R-T7 | **Expiry dates:** month/year only (e.g. `11/26`) means the **last day of that month**. **Days to expiry** `d` = expiry date − today (Beirut), in whole days. |
| R-T8 | **Search window (N-11):** the **first search runs immediately** when a request is created, so what's listed is reported and proposed within seconds. The window (`ends_at`) is how long DawaLink **keeps trying in the background for the items not yet found**: waiting for new stock and asking pharmacies. The client doesn't wait on the screen and can cancel at any time. The **window check** (N-24) runs once, shortly before the end. |
| R-T9 | **Derive, don't store:** the eligibility zone and the policy price are **pure functions of `expiry_date` and today**, computed whenever they're read. |
| R-T10 | **The clock check.** One worker loop runs every few seconds (N-26) with `now` from the app clock. It finds overdue rows using the deadlines **stored on the rows themselves**, and acts on them:<br>• expire offers;<br>• expire reservations (no-show);<br>• end search windows;<br>• expire early-release asks;<br>• run the window check;<br>• run the matching sweep over active claims (R-PRI1);<br>• run pending agent turns (R-AG4) and due follow-ups (`followup_at`, N-39);<br>• send the email outbox;<br>• once a day: retention purges and stale-inventory reminders.<br>**There is no jobs table.** Each action re-checks the row's state in its own transaction, so running it twice does nothing. If the worker stops, the next pass catches up. |
| R-T11 | **One clock:** every time limit (deadlines, offer expiry, search windows, answer times) is computed from the app clock (`now`, `today`), never the database clock. `created_at` may use real time, because it only orders "who came first". **The one exception is what protects a login** (BLD-D31): sessions, lockouts, confirmation links, the sign-up and resend limits are counted in real time, so that moving the demo clock logs nobody out and lifts no lock. |

## 2. Catalog, units, money

*Sources (checked against the real files on 2026-11-12): the Ministry of Public Health's **price list** (public .xls: code, registration number, name, strength, pack, form, manufacturer, price in LBP) joined with its **Lebanon National Drugs Database** web pages (ATC code, brand or generic, ingredients with strengths). Neither has a prescription/OTC flag or a controlled flag; R-C5 to R-C7 fill those gaps. A product that can't be matched between the two sources is left out.*

| ID | Rule |
|---|---|
| R-C1 | **Import by script** (command line), not by an admin screen. Every product stores the **source file name and date**. Admins get a **read-only** catalog view. |
| R-C2 | **Product** = one MoPH row: the Ministry's code and registration number, name, brand/generic, ingredients with strengths, dosage, form, the pack as the Ministry writes it, ATC code, public price (LBP), plus `units_per_pack` (R-C4). |
| R-C3 | **Currency:** stored in **LBP (integers)**; **always displayed in LBP and ≈ USD**. The display rate is set in config; it defaults to the rate stated on the imported list, with its date shown. Clients may give budgets in either currency; the assistant and filters convert them. Ceiling checks are always done in LBP. |
| R-C4 | **Units:** every stock and order quantity is an integer number of **units**. `units_per_pack = 1` by default, so **units = packs** and the UI says "packs". Each inventory item has `splittable = false` in the core. Prices are **per pack**. (R-D20) |
| R-C5 | **Equivalence key** = normalized set of (ingredient, strength, unit) + **form group** + **ATC code**. Only coating variants merge (tablet / film-coated / coated → *tablet*). **Modified-release never merges with immediate-release**; different routes never merge. A product with no readable strength has **no equivalents**. **An ingredient keeps its salt as written:** "amlodipine besylate" isn't merged with "amlodipine". A missed equivalent only hides an option; a wrong one could hurt someone. **The ATC code is part of the key,** because a form doesn't always say what a product is for: eye drops and ear drops are both "drops". Manual corrections live in a team-maintained **overrides file** used by the import script. |
| R-C6 | **Controlled substances are removed from DawaLink entirely.** The Ministry publishes no list that can be downloaded, so they are flagged from the international narcotic and psychotropic schedules (which Lebanon's Law 673/1998 refers to), the matching ATC classes and the overrides file. When in doubt, a medicine is flagged. The list is final as built (decision log BLD-D8). They can't be uploaded, listed, searched, reserved, watched or requested. |
| R-C7 | **Prescription required by default.** FALSE only for products on the **OTC list** (curated by the team, in the overrides file). The list starts empty, so every product shows the notice (open item O7). The flag is used **only to show a notice** (R-P1). |
| R-C8 | **A new price-list import** caps any price override above the new public price; order price snapshots never change. |
| R-C9 | **An upload row that doesn't match a product** becomes a **row error with "did you mean…" suggestions**; it's fixed in the file or added through the manual form. |
| R-C10 | **Another brand is shown, never reserved for the client** (BLD-D17). ***Same name, same medicine*** *(the owner, 2026-11-15, BLD-D29 and build plan Q38): a box that carries the name the client wrote, with the same ingredient, strength and form, is what they asked for, whichever catalog row it is: another box size, another registration, or another maker of a generic named after its ingredient. It gets a reserve card. Another brand is a box with **another name**.* Another brand of the same medicine (same equivalence key, R-C5) may be **shown** to a client who agreed to hear about other brands: where it is, its price and expiry, the line "Call the pharmacy and ask the pharmacist if this brand suits you", and a [Call] button. Whether a brand suits the client is the pharmacist's to say, never DawaLink's.<br>• **Nothing is held for another brand automatically:** a watch, a waiting request item, an offer, an early-release ask and a multi-medicine plan are always for the medicine itself.<br>• **Reserving another brand** needs the client to ask for that brand themselves, after the pharmacist agreed: in the chat or a request's thread, in a message of their own (never in a turn that no client message started); in search, by searching the brand by its own name. It is then a normal reservation; in a request that allows other brands, it secures the medicine the request was started for.<br>• **Nobody checks the call.** What the pharmacist says is outside DawaLink. When the client asks for the brand, it is reserved like any medicine; the pharmacist decides at the counter as always (R-P1). The client was told to ask first, so a refusal at the counter is theirs to bear: they cancel without penalty, or it becomes a no-show (R-N1).<br>• **The pharmacy's phone number** is added to the card when it is displayed. It never passes the LLM (R-AG8).<br>• **"Other brands OK"** (profile, request, chat) means "tell me about other brands". In a request it is changed only by the client's tap. |

| R-RQ1 | **Creation** always needs a **client tap**: [Start sourcing] on the agent's summary card in the chat. *There is no request form (the owner, BLD-D30); the search page's empty result opens the chat.* It requires an ACTIVE client, **request hours** (R-T3), **1–5 items** (product + quantity 1–3 + **days of use**, default 1) and **a location** (shared, a named area or a district, R-S2), plus optionally a max price per item and "tell me about other brands" (R-C10). `ends_at` = creation + the search window (N-11). |
| R-RQ2 | **Limits:** ≤ 2 open requests per client, checked when a request is started. A request that opened again (R-RQ12) is never refused for this limit; it counts like any open request when the client starts a new one. Their orders count toward R-L1/R-L2. |
| R-RQ3 | **The agent runs a turn on a request when** (decision events):<br>• it is submitted;<br>• the client writes in the request thread;<br>• a reservation for an item is marked not available, or cancelled by the system (also when this opens a closed request again, R-RQ12);<br>• an early-release request ends UNFULFILLED;<br>• the **window check** finds items not secured (N-24);<br>• a group reserve left some items unticked (R-RQ6);<br>• the client accepts a change the agent proposed: other brands, or a higher budget (decision log BLD-D20). |
| R-RQ4 | **Autonomy boundary.**<br>• **The agent may, without asking:** search; set the area to search around from a place the client named in chat (R-S2); plan; open claims (matching); send early-release asks (R-E rules); schedule **one follow-up check at a time** inside the window (N-39); escalate.<br>• **It must get a client tap for:** reserving; accepting an offer; changing constraints (budget, hearing about other brands); removing an item; cancelling.<br>• **Another brand is only ever shown** (R-C10): the agent never reserves, plans or waits for one on its own.<br>• **It never ranks clients** (R-PRI), and it never gives up on an item by itself: items become UNAVAILABLE only when the window ends. |
| R-RQ5 | **Multi-medicine planning:** the agent calls the deterministic tool `plan_basket(items, constraints)`. It returns candidate plans: sets of visible listings covering the items, where **one medicine's quantity may be split across pharmacies** (Concor ×2 = 1 at A + 1 at B). Every plan uses only boxes of the asked medicines themselves (never another brand, R-C10) that **fit** (R-F1), and comes with its **route**: the best order to visit its pharmacies and the total travel time (R-RT2). Candidates are listed by **total travel time**, then **number of pharmacies**, then **total price**, but **the agent decides** which plan to recommend (R-AG9). It uses what the client said (no car, only after 18:00, cheapest…), explains why in one sentence, and proposes it with up to 2 alternatives. Items with no listing go to a claim and/or early release. Only the plans that cover the most units are returned, within the limits of N-48. **Every stop of a plan earns its place:** without any one of its pharmacies, the plan would get fewer units or cost more. Two pharmacies often ask the same price; visiting both where one is enough is a detour, not an alternative. |
| R-RQ6 | **Per-item reporting and plan cards.**<br>• The agent **always tells the client, item by item, what it found and what it didn't**. Example: "Found Concor at Pharmacy A. Glucophage and Aspirin aren't listed: I'm asking 2 pharmacies and watching for new stock."<br>• Plan cards are grouped **per pharmacy** and can hold **any subset** of the items (one card with only Concor is normal).<br>• The group sheet lists the card's items with **checkboxes, all ticked by default**. **[Reserve these]** reserves the ticked items **all or none**.<br>• If an item fails at tap time (just taken, limit reached), **nothing in that card is reserved**. The agent says which item failed, offers a new card with the remaining items, and keeps sourcing the failed one.<br>• **Unticked items** go back to SEARCHING, and the agent gets a turn. |
| R-RQ7 | **A covered need:** when all of an item's units are reserved, the item is SECURED, its claim is FULFILLED, and its open offers and asks are withdrawn (R-W3). |
| R-RQ8 | **Thread:** each request has its own conversation (`kind = request`). Informational events post template cards there. The chat assistant can read a request's status through a tool. |
| R-RQ9 | **Closing:** when every item is final (SECURED, UNAVAILABLE, CANCELLED), **or** when `ends_at` has passed **and no offer is pending**. Offers made before the end stay valid for their 2 hours. At closing:<br>• open claims and asks are withdrawn;<br>• non-final items → UNAVAILABLE;<br>• outcome: every item SECURED → FULFILLED; at least one unit secured → PARTIAL; none → UNFULFILLED;<br>• the summary is sent (CN-17).<br>Client cancel → CANCELLED, and non-final items are cancelled. **After closing, the outcome doesn't change:** later pickups, cancels or no-shows are recorded on the orders only. The one exception is R-RQ12. |
| R-RQ10 | **Per-request agent limit:** ≤ 20 agent turns per request (N-17). Above that → escalate (reason `cannot_resolve`). |
| R-RQ11 | **The client's own cancel or no-show.** When the client cancels a reservation that belongs to an open request, or doesn't come for it, that medicine is finished in the request: its item becomes CANCELLED, nothing is searched again and no agent turn runs. The other medicines carry on. (After [Not available] or a system cancel, the search does start again: R-RQ3.) |
| R-RQ12 | **A box lost after the request closed** (the owner, 2026-11-15). A request closes as soon as every medicine is reserved, often long before its 6 hours are over. If a reservation of one of its medicines is then marked **not available**, or cancelled by the system, **before `ends_at`**, the request **opens again**:<br>• that medicine goes back to SEARCHING (or WAITING, if a claim was open for it: the claim is active again, at its place in the queue);<br>• the outcome is cleared, a line in the thread says the request is open again, and the agent runs a turn (R-RQ3), exactly as for an open request;<br>• `ends_at` doesn't move: the client was promised 6 hours, not more;<br>• it closes again by R-RQ9, with a new summary.<br>**It doesn't open again:** after `ends_at`; when the client cancelled the request; for a medicine the client gave up on. What the client cancelled or didn't collect while the request was closed stays given up when it opens again (R-RQ11). |
### R-P1 Prescription notice
For products with `prescription_required = TRUE`, the following show **"📄 Prescription needed: bring it to the pharmacy"**:
- the search card;
- the reserve sheet;
- the agent;
- the reservation email.

DawaLink **doesn't ask when the client will have it**, and it doesn't change the pickup time. **The pharmacist checks the prescription at the counter**, and may refuse to hand over without one. The client can then come back before the deadline, or cancel without penalty.

### R-PRI Allocation priority: first come, first served (ADR-003, amended)
| ID | Rule |
|---|---|
| R-PRI1 | **When matching runs:**<br>• newly available stock (an item enters the window, an upload or manual edit, a lock released, a listing resumed, a pharmacy reinstated, a price dropping below a claim's max);<br>• when a claim is **created**;<br>• in the clock check's **sweep of all active claims** (R-T10), so stock that's already visible is never missed. |
| R-PRI2 | **Order: first come, first served** = the earliest claim (`created_at`, then `id`). Computed by code, with the reason logged (e.g. "allocated to claim C-12: waiting since 10:02"). Each winning claim gets an OFFERED hold for its missing units while stock remains. **Reach:** pharmacies within the claim's travel-time reach (N-23); only boxes that fit (R-F1). |
| R-PRI3 | **Eligibility:** claims whose client is not ACTIVE, or would exceed R-L1/R-L2, are **skipped** for this round, with the reason logged. The next claim gets the unit. |
| R-PRI4 | **Nobody can change the order:** not the agent, not an admin. If a client claims an emergency, the agent:<br>• explains the rule;<br>• for a medical emergency, tells the client to contact a doctor or emergency services;<br>• offers human help (escalation `emergency_claim`).<br>The human can help and reply, but can't change the order. |
| R-PRI5 | **Direct reservations** (a client tapping a visible listing) are first come, first served at the tap. R-PRI governs only holds created by matching. |
| R-PRI6 | A client who misses out is told only "someone who asked earlier was offered it first", never who. |

### R-S Search and ranking
| ID | Rule |
|---|---|
| R-S1 | Login required; only visible listings; page size 20. |
| R-S2 | **Location** (the professor's guidance):<br>• **Client:** shares their location from the phone for a search, a chat or a request ("Use my location"), **or marks the place on a map** ("Pick on the map", BLD-D16: the point is treated exactly like a shared location), or picks a **district** (its reference point is used). **With nothing shared, a search starts from the client's home** (BLD-D40): the place saved on the map in their profile, else the centre of their home town, else their home district's reference point. **At sign-up and in the profile the client gives one of two** (BLD-D42): a place on the map, which [Use my location] can put where the device is, or a district with an optional town. A client who gave only a place has no district: code never guesses one from the point. A saved place is rounded like any location, must be in Lebanon, and is kept until the client removes it. **Or they name their area in the chat** ("I'm in Hamra", BLD-D14): the agent passes the name to code (`set_area`), code looks it up in **our own list of areas** (the 26 districts, the well-known neighbourhoods, and the towns and villages of OpenStreetMap, BLD-D15) and uses that area's centre. Only a name written like a listed one is accepted; anything else is offered back as "did you mean", and the agent or the client chooses. **A name that exists in several districts is never chosen by code:** the agent asks which one ("Hadath in Baabda or in Baalbek?"). The place named last replaces an earlier location of that chat. Nothing the client typed is sent to an outside service. It's stored **rounded to about 100 m**, only on that conversation, request or claim, and purged with them (R-RET).<br>• **Pharmacy:** sets a **map pin** at registration. An admin checks it at approval, and only an admin can move it after.<br>• **Coordinates never reach the LLM** (INV-24): tools give it travel times, distances and area names. An area the client named is known to the agent **by its name only**; its times are counted from the area's centre, so the agent says "about". |
| R-S3 | **Best match:** boxes that fit (R-F1) → shortest travel time (by car, or walking when the client says so) → price ascending → expiry soonest. Other sorts: nearest, cheapest, latest expiry. Each result shows the travel time by car and on foot. |
| R-S4 | **Search shows the medicine that was searched, never another brand** (BLD-D17; the "include alternatives" filter is gone). Another brand is shown only by the assistant (R-C10). A client who wants another brand searches it by its own name. |
| R-S5 | Availability shown exactly up to 5, then "5+". |

### R-F Expiry fit: days of use and pickup day (the professor's guidance)
| ID | Rule |
|---|---|
| R-F1 | **A box fits** a client if it's still valid on the **last day of use**: `expiry_date ≥ pickup_day + days_of_use − 1`.<br>*Examples* (today Oct 20, a box expiring Oct 21):<br>• 1 day of use, picked up today → used Oct 20 → ✅ fits;<br>• 1 day of use, picked up tomorrow → used Oct 21 → ✅ fits (still valid on its expiry day);<br>• 3 days of use, picked up today → would be used Oct 20–22 → ❌ doesn't fit.<br>*The professor's example:* 12 days of use → a box expiring in 2 days ❌, one expiring in 15 days ✅.<br>*The owner's example* (a later pickup day): a box expiring in 7 days, at a pharmacy that accepts pickups on its next 3 days. Picked up on the third day, only 5 days are left:<br>• 2 days of use → ✅ fits on every day;<br>• 7 days of use → ✅ fits if picked up today or tomorrow, ❌ not on the third day;<br>• 8 days of use → ✅ today only. |
| R-F2 | **Days of use** come from the client: the agent asks, and the search page and forms have an optional field. If the client doesn't know → **1 day** (N-44), and every card and agent message shows the expiry date with a warning: "Expires 25 Oct: make sure that's enough for your treatment; the pharmacist can check your prescription." DawaLink never judges what the right duration is (logistics only). |
| R-F3 | **Pickup day:** today (only if the pharmacy stays open at least N-42 longer), or one of its next open days within its pickup time (N-6): **3 open days at most**. Only days on which the box fits are offered. **These are the only pickup days, everywhere:** the search filter, the reserve screen and the agent's tools all take the pickup day as a **date** and check it against this rule (decision log BLD-D1). |
| R-F4 | **No match:** if no visible box fits, the client is told plainly: "No match: the available boxes expire too early for 12 days of use (the latest expires 28 Oct)." The agent can then watch for new stock or ask pharmacies (early-release boxes are 181–270 days from expiry, so they fit almost any use). |
| R-F5 | **The fit is always checked in code:** in search, in the tools, at the tap, in matching and when an offer is accepted (INV-25). |
| R-F6 | **A later pickup day leaves fewer days before the box expires** (decision log BLD-D2). When the client says which day they'll come, the search page and the agent's tools count the fit from **that day**, so a box that fits today may not fit on the last day the pharmacy accepts. Every option carries the pickup days on which it still lasts, and a flag when the expiry, not the pharmacy, is what rules a later day out. The client is then told the last day that works: "Pick it up by Wed 21 Oct: after that, it won't last your 7 days." Code does this arithmetic; the agent never works out a date (N-49). |

### R-RT Routes and travel time
| ID | Rule |
|---|---|
| R-RT1 | **Travel times** are computed in code by a routing service (OpenRouteService, built on OpenStreetMap data), **by car and on foot**, from the client's rounded location to each candidate pharmacy. Results are cached (N-43). If the service fails or is too slow (N-41), **straight-line distance** is used instead, with an estimated time labeled "about" (`source = straight`). |
| R-RT2 | **Routes for plans:** for a plan with several pharmacies, code tries every visiting order (starting from the client's location) and keeps the shortest total travel time. |
| R-RT3 | **Reach** for automatic actions (matching offers, early-release asks): pharmacies within N-23 by car from the client's location. |

### R-AS Assistant limits
- Message ≤ 1,000 chars.
- ≤ 20 messages per minute and ≤ 100 per day per client.
- ≤ 6 tool calls per turn.
- ≤ 20 agent turns per request.
- A daily token budget per client: **3,000,000 tokens**, counting every token a client's turns read or write, cached ones included. Measured in build step 5: a turn uses about 30,000, so this is about 100 turns, the same as the daily message limit. *Approved by the owner (2026-11-14, BLD-D12).* Over budget → degraded mode for that client until midnight.
- **Global spend caps (N-46):** a daily and a monthly cap on LLM spend for the whole system. Reaching either → degraded mode for everyone until the next day or month. The provider's own spend limit is set as a hard backstop outside our code (`10` TM-D6).
- Conversations are kept 30 days after their last activity, or after the request closes.

### R-AU Accounts and security
| ID | Rule |
|---|---|
| R-AU1 | Password ≥ 10 chars **with a capital letter, a small letter, a number and a symbol** (the owner, 2026-11-18, BLD-D40; plain ASCII letters and symbols, as Cognito counts them), not in the top-10k list, argon2id. A common word with only numbers and symbols around it is still the common word. |
| R-AU2 | 5 failed logins in 15 min → locked 15 min (admins: other admins are alerted). **Also per network address (N-52; the owner, 2026-11-17, Q48):** after 30 failed tries from one address in 15 minutes, on any accounts, every login from that address is refused until the 15 minutes are over. A login that works is never counted, so a room of people behind one address is not affected. |
| R-AU3 | **Server-side sessions (DR2-B4):** login creates a session. The browser holds only a random token, which it sends in the `Authorization` header; the server stores its hash. Valid 7 days (admins 12 h). **Logout, a password change or a suspension revokes it immediately.** Admins also enter a one-time code (R-AU6). |
| R-AU4 | Email verification link 24 h, single use, stored hashed. **Following it logs the user in.** Pharmacies confirm their email too, before they enter the approval queue (R-AU7). **A pharmacy registration whose email is never confirmed is deleted by the daily clean-up once no link is good any more** (the owner, 2026-11-17, Q49): its licence number and its phone are free again, and the pharmacy simply registers again. A client's unconfirmed account is kept. *(Password reset postponed.)* |
| R-AU5 | ≤ 5 sign-ups per IP per hour. The assistant and requests need a verified email. |
| R-AU6 | **Admin two-factor login** (`10` TM-D8): after the password, admins enter a TOTP code from an authenticator app. The secret is created by the `create_admin` command (the only way to create an admin, A-D1) and stored encrypted; a lost phone means re-running the script (no recovery flow). Contact-detail views (`pii.view`) are limited (N-47), and the other admins are alerted above the limit (R-AL). |
| R-AU7 | **Registration never reveals whether an email has an account** (`10` TM-D7). Client and pharmacy registration always answer "check your email". A new email gets the verification link (CN-1); an email that already has an account gets "you already have an account: just log in" (CN-18), at most once per address per day (N-47). Login computes a password hash even for unknown emails, so its timing reveals nothing. |
