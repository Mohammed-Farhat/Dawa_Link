# Evaluation datasets: data sheets

What each dataset is, where it comes from and what it can't tell us (course requirement G-7; plan in [`docs/08_evaluation.md`](../../docs/08_evaluation.md) §2).

## In short

| Dataset | File | Made by | Size now | Whole set |
|---|---|---|---|---|
| **U-set**, understanding | `understanding.jsonl` | Written by Claude, checked by the owner (first 60 read on 2026-11-15) | 180 | 300 (180 here, 120 held out) |
| **R-set**, safety | `safety.jsonl` | Written by Claude, checked by the owner (first 28 read on 2026-11-15) | 70 | 120 (70 here, 50 held out) |
| **S-world**, the simulated world | `../world/` | Generated by code from a seed; road times from OpenRouteService | built | 30 pharmacies, 200 clients, 13,620 trips |
| **P-set**, plan baskets | `plans.jsonl` | Generated by code from a seed; the answers by trying everything | 50 | 50 baskets, 200 rankings |

There is **no real patient or client data** anywhere: every message is invented, and every client and pharmacy of the simulated world is generated.

## U-set and R-set

- **What:** messages a client could send, with the correct reading (U-set) or the conditions that must hold after the agent answers (R-set). The format and the rules are in [`LABELING_GUIDE.md`](LABELING_GUIDE.md). Since the agent asks before it searches (decision log BLD-D28), a U-set case can take two turns: the case's client answers the agent's question once, from the case's labels (a car unless `no_car`, the labeled day or today, the labeled days of use or 7). The cases themselves didn't change.
- **Source:** written for this project, from scratch. No message is copied from a real conversation.
- **Languages:** Lebanese Arabic in Latin letters (Arabizi), Arabic script, English, and mixes.
- **Medicines:** a case names a medicine as a person does ("concor", "5mg"). When a suite runs, the name is matched to the local copy of the Ministry of Public Health's public price list. No line, price or ID of that list is in these files.
- **Splits:** this folder is the **development** part, used freely while building. The **held-out** part is written in a separate session, in `eval/heldout/`, and is read only by the final runs (`docs/08` §6.3).
- **Checking:** `author` wrote the case, `checked_by` agreed with its label. 20% are labeled twice, blind.
- **Check the files:** inside `backend/`, `uv run --env-file ../.env python -m dawalink.evals.validate`.

### Known limits

- The same people built the agent and wrote the cases. The held-out part and the blind second labels reduce this, and don't remove it.
- The sets are small. A difference of a few points between two models is not a finding unless its confidence interval says so.
- Invented messages are tidier than real ones. Real clients will be messier, and angrier.
- "Today" is fixed (Monday 2026-11-16), so weekday expressions are tested for one week only.

## P-set

- **What:** 50 baskets of 1 to 5 medicines, the boxes that could serve each, the trips between the places, and the 3 best plans in each of the four orders a client can ask for (nearest, fewest trips, cheapest, walkable). It checks the planner behind the `plan_basket` tool, which is plain code: no model is involved.
- **Source:** generated by `python -m dawalink.evals.build_plan_set` from seed 2026. The file is never edited by hand; a test rebuilds it and compares.
- **Medicines and prices are invented:** `m1` to `m5`, a made-up full price less 25%, 40% or 60%. Nothing comes from the Ministry's list.
- **Trips:** the simulated world's road table (`../world/travel.json`), from one of its client points to 2 to 14 of its pharmacies and between them. Travel times computed by openrouteservice.org; road data © OpenStreetMap contributors.
- **Answers:** found by `evals/plan_oracle.py`, which tries every quantity from every box, every set of up to 4 pharmacies and every visiting order. What "best" means is written at the top of that file.
- **Check it:** inside `backend/`, `uv run python -m dawalink.evals.plan_set`.

**What is in it** (of 50 baskets):

| Situation | Baskets |
|---|---|
| The best plan has 2 stops or more | 33 |
| A quantity must be split across pharmacies | 26 |
| Not everything can be found | 21 |
| Two pharmacies ask the same price for a medicine | 39 |
| More than 8 pharmacies have a box | 6 |
| "Cheapest" changes the first plan | 18 |
| "Walkable" changes the first plan | 5 |
| "Fewest trips" changes the first plan | 3 |
| Fewer than 3 plans exist | 29 |

### Known limits

- The baskets are random, not real: real shelves may be shaped differently (for example one big pharmacy that has nearly everything).
- No basket has more than 16 pharmacies with a box, so the planner's limit on how many pharmacies it weighs (`04` N-48) isn't exercised here; service tests cover it (`backend/tests/services/test_planning.py`).
- "Fewest trips" changes the winner in only 3 baskets, so that order is the least tested of the four.
- The answer key and the planner follow the same written definition of a plan ("every stop earns its place", `docs/04` R-RQ5), so the set can't tell whether that definition is the right one: it checks that the planner applies it. The first plan is also checked another way, by a test that tries every way to fill 300 random baskets without that definition (`backend/tests/unit/domain/test_planning.py`).
- Road times are whole minutes. In this set no route through one more pharmacy adds up to less than the direct one; on other roads it can, by a minute. Such a detour buys nothing, and neither the answer key nor the planner takes it.
